2 · การติดตั้ง (ละเอียด)

เมื่อเปิดครั้งแรก ระบบปฏิบัติการจะเตือนความปลอดภัย เพราะแอปแจกภายในหน่วยงาน ไม่ได้ผ่าน App Store / Microsoft Store — เป็นเรื่องปกติ ปลดล็อกครั้งเดียวจบ

🍎 macOS

เครื่องที่รองรับ: Mac ชิป Apple Silicon (M1/M2/M3/M4) เท่านั้น · macOS 11 (Big Sur) ขึ้นไป · ไม่รองรับ Mac ชิป Intel

1
ดับเบิลคลิกไฟล์ .zip เพื่อแตกไฟล์
2
ลาก "Security Audit Toolkit.app" ไปไว้ในโฟลเดอร์ Applications (วางบน Desktop ก่อนก็ได้)
3
ปลดล็อกครั้งแรก — เลือกทำวิธีใดวิธีหนึ่ง (ด้านล่าง)

วิธีปลดล็อก macOS Gatekeeper (ครั้งแรกครั้งเดียว) เมื่อขึ้นข้อความ "…can't be opened because Apple cannot check it for malicious software":

  • วิธีที่ 1 (แนะนำ เร็วสุด): คลิกขวา (หรือกด Control ค้างแล้วคลิก) ที่แอป → เลือก Open → ในกล่องเตือน กด Open อีกครั้ง · ครั้งต่อไปดับเบิลคลิกได้ปกติ
  • วิธีที่ 2 (สคริปต์คลิกเดียว): ดับเบิลคลิกไฟล์ Unlock_Security.command ที่แนบมาในโฟลเดอร์
  • วิธีที่ 3 (ผ่านการตั้งค่า): เมนู Apple → System Settings → Privacy & Security → เลื่อนลงหัวข้อ Security → กด Open Anyway แล้วใส่รหัสผ่านเครื่อง
  • วิธีที่ 4 (ผู้ดูแลระบบ / Terminal): xattr -cr "/Applications/Security Audit Toolkit.app"

🪟 Windows

เครื่องที่รองรับ: Windows 10 / 11 (64-bit) หรือ Windows Server 2016/2019/2022 · ไม่ต้องติดตั้ง Python

1
คลิกขวาที่ไฟล์ .zip → Extract All… เพื่อแตกไฟล์ (สำคัญ: ต้องแตกออกก่อน อย่าเปิด .exe จากข้างใน .zip โดยตรง)
2
เปิดโฟลเดอร์ที่แตกไว้ แล้วดับเบิลคลิก "Security Audit Toolkit.exe"
3
ถ้ามีจอฟ้าเตือน ให้ปลดล็อก (ด้านล่าง)

วิธีปลดล็อก Windows SmartScreen เมื่อขึ้นจอฟ้า "Windows protected your PC":

  • วิธีที่ 1 (แนะนำ): คลิก More info → กดปุ่ม Run anyway · ครั้งต่อไปจะไม่เตือนอีก
  • วิธีที่ 2 (สคริปต์คลิกเดียว): ดับเบิลคลิกไฟล์ Unlock_Security.bat ในโฟลเดอร์
  • วิธีที่ 3 (ปลดบล็อกที่ไฟล์): คลิกขวา Security Audit Toolkit.exe → Properties → แท็บ General ด้านล่าง ติ๊ก Unblock → Apply → OK

3 · การใช้งาน

ใช้งานได้ 2 โหมด — GUI (หน้าจอ) และ CLI (บรรทัดคำสั่ง) โดยทั้งคู่ใช้เอนจินตรวจตัวเดียวกัน

โหมด GUI — 5 ขั้นตอน

1
เป้าหมาย & โหมด — ใส่เป้าหมาย (โฮสต์/IP/ไฟล์รายชื่อ) และเลือกโหมดสแกน
2
เลือกรายการ CVE — เลือกชุด CVE ที่ตรวจ หรือใช้ทั้งหมด
3
8 กลุ่ม ThaiCERT — ดูว่าการสแกนครอบคลุมกลุ่มใดบ้าง
4
การสแกนสด (Live) — กด "เริ่มการสแกน" ดู log และแถบคืบหน้าแบบเรียลไทม์
5
แฟ้มรายงาน & ผลลัพธ์ — เปิดรายงานที่สร้างให้อัตโนมัติ

โหมด CLI — เลือกโหมดเป้าหมาย

ธงคำสั่งใช้เมื่อตัวอย่าง
--targetเป้าหมายเดี่ยว--target host.example.com
--cidrช่วง IP ทั้งวง--cidr 192.168.1.0/24
--wildcardค้นซับโดเมนทั้งโดเมน--wildcard *.example.com
--listตรวจจากไฟล์รายชื่อ--list hosts.txt
--pipelineตรวจเจาะ + ยืนยันช่องโหว่--pipeline host --i-own-this-target
โหมด --pipeline (ทดสอบเชิงรุก/ยืนยัน RCE) บังคับต้องใส่ --i-own-this-target เพื่อยืนยันว่าเป็นเจ้าของ/ได้รับอนุญาต

5 · เทคนิคในการตรวจสอบ

Fingerprint
อ่าน header / banner / HTML เพื่อระบุเทคโนโลยีและเวอร์ชัน
จับคู่ CVE
เทียบเวอร์ชันกับคลัง CVE ในตัว + ชุด CVE อดีต (historical)
Online CVE (CIRCL)
ค้น CVE สดตามเวอร์ชันที่พบ (เปิด/ปิดได้ · มีแคช)
ค้นซับโดเมน
รวบรวมจากหลายแหล่ง (crt.sh, OTX ฯลฯ) เพื่อขยายพื้นผิว
พอร์ต + OS/MPTCP
สแกนพอร์ตที่เปิด และตรวจสัญญาณ OS/เคอร์เนล Linux
TLS & MAC/OUI
ตรวจค่า TLS และผู้ผลิตอุปกรณ์จาก MAC (เฉพาะในวง LAN)

ช่องโหว่ที่ตรวจ — ผลกระทบถ้าถูกแฮก

เครื่องมือตรวจ CVE หลัก 14 รายการ ใน 5 กลุ่มเทคโนโลยี — ด้านล่างอธิบายว่า "ถ้าแฮกเกอร์ใช้ช่องโหว่แต่ละตัว ระบบจะเป็นอย่างไร" แบบเข้าใจง่าย

เข้าใจระดับความรุนแรงก่อน

Critical ร้ายแรงสุด — มักถึงขั้น "ยึดเครื่อง/รันโค้ดได้" ต้องแก้ทันที   High ร้ายแรง — ควรแก้เร็ว   Medium ปานกลาง — ควรวางแผนแก้

คำที่เจอบ่อย — RCE (Remote Code Execution): แฮกเกอร์สั่งรันคำสั่งของตัวเองบนเซิร์ฟเวอร์จากระยะไกล = เท่ากับ "ยึดเครื่อง" เป็นผลกระทบที่อันตรายที่สุด

🐘 PHP (3 รายการ)

ช่องโหว่ความรุนแรงถ้าแฮกเกอร์ใช้ช่องนี้ ระบบจะเป็นยังไง
CVE-2026-109618
PHP Use-After-Free (OOM)		CriticalPHP เผลอใช้หน่วยความจำที่คืนไปแล้วซ้ำ → แฮกเกอร์เขียนทับจน รันโค้ดบนเซิร์ฟเวอร์ได้ (RCE) = ยึดเว็บทั้งเครื่อง
เปรียบเทียบ: ห้องที่เช็คเอาท์แล้วแต่กุญแจเก่ายังเปิดได้ คนร้ายแอบเข้าไปใช้
CVE-2026-109619
PHP Use-After-Free (global state)		Criticalคล้ายข้างบน (UAF อีกจุด) → รันโค้ด/ยึดเครื่อง หรือทำเว็บล่ม
CVE-2026-115560
Session Upload Progress Injection		Medium-Highอาศัยกลไกอัปโหลดของ PHP ฝังโค้ดลงไฟล์ session แล้ว (ถ้ามีช่อง LFI) สั่งรัน → RCE — นี่คือช่องที่ฟีเจอร์ RCE Verify ของเราใช้พิสูจน์
เปรียบเทียบ: แอบสอดจดหมายไว้ในตู้รับของ แล้วหลอกให้พนักงานหยิบไปอ่าน

🌐 NGINX / เว็บเซิร์ฟเวอร์ (5 รายการ)

ช่องโหว่ความรุนแรงถ้าแฮกเกอร์ใช้ช่องนี้ ระบบจะเป็นยังไง
CVE-2026-15176
Heap Buffer Overflow (alias+rewrite)		Criticalส่งคำขอพิเศษให้ NGINX เขียนข้อมูล ล้นที่เก็บ → เว็บ ล่ม หรือถูก ยึด (RCE)
เปรียบเทียบ: เทน้ำใส่แก้วจนล้นไปท่วมของข้างๆ จนระบบรวน
CVE-2026-93479
Heap Buffer Overflow (map+regex)		Criticalบัฟเฟอร์ล้นอีกรูปแบบ → เว็บล่ม / ถูกยึด เช่นกัน
CVE-2026-97205
Use-After-Free (AIO+SSI)		Criticalใช้หน่วยความจำที่คืนแล้วซ้ำในตัว NGINX → crash หรือ RCE
CVE-2026-95101
Request Body Injection (HTTP/3)		Mediumแทรกข้อมูลในคำขอ HTTP/3 → อาจ ลักลอบส่งคำขอปลอม/ข้ามการตรวจ (เช่นหลบ WAF)
CVE-2026-97629
Session Forgery (TLS tickets)		Mediumปลอม session จาก TLS ticket → อาจ สวมรอยผู้ใช้คนอื่น
เปรียบเทียบ: ปลอมตั๋วเข้างานที่ยังใช้ซ้ำได้

🟢 Node.js (4 รายการ)

ช่องโหว่ความรุนแรงถ้าแฮกเกอร์ใช้ช่องนี้ ระบบจะเป็นยังไง
CVE-2026-111497
Brotli Out-of-bounds Write (RCE)		Criticalส่งข้อมูลบีบอัด Brotli ที่ปั้นมา ทำให้เขียนหน่วยความจำนอกขอบเขต → RCE / ยึดเครื่อง
CVE-2026-105483
TLS Cert Validation (Unicode IP)		Highข้ามการตรวจใบรับรอง TLS → ดักกลางทาง (Man-in-the-Middle) แอบอ่าน/แก้ข้อมูลที่ควรเข้ารหัส
เปรียบเทียบ: ปลอมบัตรประชาชนแล้วแอปหลงเชื่อ เลยคุยความลับกับคนผิด
CVE-2026-106069
TLS Endpoint Identity Bypass		Highข้ามการยืนยันตัวตนปลายทาง TLS → MITM เช่นกัน ข้อมูลที่ส่งอาจถูกดัก
CVE-2026-105482
DNS NUL Domain Bypass		Highหลอกการตรวจชื่อโดเมนด้วยอักขระพิเศษ → อาจพาแอป ไปต่อเซิร์ฟเวอร์ของแฮกเกอร์ (SSRF/เปลี่ยนทาง)

🦊 GitLab (1 รายการ)

ช่องโหว่ความรุนแรงถ้าแฮกเกอร์ใช้ช่องนี้ ระบบจะเป็นยังไง
CVE-2026-110264
GitLab		Highช่องโหว่ในตัว GitLab → อาจ เข้าถึงซอร์สโค้ด/ความลับใน repo หรือข้อมูลโปรเจกต์โดยไม่ได้รับอนุญาต
กระทบหนักเพราะซอร์สโค้ดมักมีรหัส/คีย์ของระบบอื่นอยู่ด้วย

🧩 OS / Kernel (1 รายการ)

ช่องโหว่ความรุนแรงถ้าแฮกเกอร์ใช้ช่องนี้ ระบบจะเป็นยังไง
CVE-2026-98432
Linux Kernel TCP Use-After-Free		Criticalส่ง packet พิเศษไปพอร์ตที่เปิด → เกิด UAF ที่ แกนกลาง (kernel) ของระบบ → อาจ ยกระดับเป็น root หรือทำเครื่องล่ม
กระทบหนักสุดเพราะถ้าโดนที่เคอร์เนล = คุมได้ทั้งเครื่อง ไม่ใช่แค่เว็บ
สรุปภาพรวม: ช่องโหว่ระดับ Critical (PHP/NGINX UAF+overflow, Node Brotli, Linux kernel) ส่วนใหญ่นำไปสู่ RCE = ยึดเครื่อง จึงต้องแก้ก่อน · ระดับ High (Node TLS/DNS, GitLab) มักเป็น ดักข้อมูล/เข้าถึงข้อมูลโดยไม่ได้รับอนุญาต · ระดับ Medium (NGINX HTTP/3, TLS ticket) มักเป็น หลบการตรวจ/สวมรอย
หมายเหตุ: เครื่องมือ "ตรวจจากภายนอก" บอกได้ว่า เวอร์ชันเข้าข่ายช่องโหว่หรือไม่ — การยืนยันว่าถูกโจมตีได้จริงและระดับผลกระทบจริง ควรดูสถานะ (ดูหัวข้อ "การยืนยันผล") และตรวจซ้ำบนเครื่อง

6 · การยืนยันผล (Confirm)

แต่ละช่องโหว่ถูกจัดระดับความมั่นใจเป็น "สถานะ" ไม่ใช่แค่พบ/ไม่พบ

สถานะความหมาย
vulnerableยืนยันแล้วว่ามีช่องโหว่จริง (เช่น ทดสอบ RCE ผ่าน)

patched / n/aแก้แล้ว หรือไม่เกี่ยวข้องกับระบบนี้
unknownตรวจจากภายนอกไม่ได้ → ต้องยืนยันบนเครื่อง
โหมด --pipeline จะทดสอบยืนยัน RCE จริง (ต้อง --i-own-this-target) และเก็บ หลักฐาน Chain of Custody ไว้ในไฟล์ JSON

RCE Verify ทำงานยังไง · ปลอดภัยไหม?

RCE Verify คือการ "พิสูจน์ว่าช่องโหว่มีอยู่จริง" โดยเก็บหลักฐาน — ไม่ใช่การเจาะเพื่อยึดเครื่องหรือทำลายระบบ

หลักการแบบเข้าใจง่าย

แทนที่จะ "เดา" จากเลขเวอร์ชันเฉย ๆ เครื่องมือจะลองสั่งให้เซิร์ฟเวอร์ ตอบข้อมูลระบบกลับมา ผ่านช่องโหว่ PHP Session Upload + LFI (CVE-2026-115560) — เปรียบเหมือน "เคาะประตูแล้วขอให้บอกชื่อ" เพื่อพิสูจน์ว่าประตูเปิดได้จริง

1
ฝากโค้ดเล็ก ๆ ไว้ในไฟล์ session ของ PHP (ผ่านการอัปโหลด — เนื้อไฟล์เป็นข้อความ benign)
2
เรียกไฟล์นั้นผ่านช่องโหว่ LFI ให้โค้ดทำงาน
3
ถ้าเห็น "รหัสลับ" (marker) ตอบกลับมา = ยืนยันว่าช่องโหว่มีจริง 100%
4
(สำรอง) ถ้ารันโค้ดไม่ได้ จะลองอัปไฟล์ marker แล้วอ่านกลับ → พิสูจน์แค่ว่า "เขียน+อ่านไฟล์ได้"
คำสั่งที่รันบนเป้าหมายมีแค่ id (ดูว่าเป็นผู้ใช้อะไร) และ php_uname() (ดูข้อมูลระบบ) — อ่านอย่างเดียว ไม่แก้ ไม่ลบ ไม่เพิ่มอะไร

ส่งผลกับเป้าหมายยังไง

ไม่ทำลายข้อมูล
ไม่ลบ/ไม่แก้ไฟล์ ไม่ฝัง backdoor ไม่ยกระดับสิทธิ์ ไม่ลงโปรแกรมใด ๆ
โหลดเบา
ยิง HTTP แค่ไม่กี่ request ต่อเป้าหมาย
ทิ้งร่องรอยเล็กน้อย
เขียนไฟล์ session ชั่วคราวเล็ก ๆ บนเครื่อง — เครื่องมือไม่ลบให้ อาศัย PHP เคลียร์เอง
เห็นใน log
log เซิร์ฟเวอร์จะมี marker RMUTCERT_* และ User-Agent "authorized testing only" (ตั้งใจให้ตรวจย้อนได้)

ด่านความปลอดภัยที่มีอยู่แล้ว

  • จำกัด Private IP — ถ้าเป้าหมายไม่ใช่ IP ภายใน จะถูกปฏิเสธ เว้นแต่ใส่ --i-own-this-target (แล้วเตือนว่าเป็น public)
  • ถาม YES ก่อนรัน (โหมด interactive) — ต้องพิมพ์ YES ยืนยันเอง
  • เก็บหลักฐาน Chain-of-Custody — transcript + SHA-256, metadata, summary, rce_proof บันทึกชื่อผู้ทดสอบ (operator)

แล้วต้องกังวลไหม?

ปลอดภัยในแง่ "ไม่ทำระบบพัง / ข้อมูลไม่หาย" — คำสั่งเป็น read-only, เนื้อไฟล์ benign, มีด่านกัน และเก็บหลักฐานครบ
แต่ต้องเข้าใจ: มัน "รันโค้ดจริง" บนเป้าหมายที่มีช่องโหว่ และทิ้งร่องรอย → ใช้เฉพาะระบบที่ได้รับอนุญาต · ระวังบน production (อาจไป trigger WAF/IDS หรือทำ log รก) · โหมด GUI/pipeline จะข้ามคำถาม YES เหลือแค่ด่าน private-IP + --i-own-this-target จึงต้องมั่นใจเป้าหมายก่อนสั่ง
สรุป: ไม่ต้องกังวลเรื่องทำระบบเสียหาย แต่เพราะมันรันโค้ดจริงและทิ้งร่องรอย จึงไม่ควรยิงมั่ว — ยิงเฉพาะเป้าหมายที่ได้รับอนุญาต และควรแจ้ง/นัดหมายทีมดูแลระบบก่อน โดยเฉพาะระบบที่ให้บริการจริง

7 · ขอบเขต: 8 กลุ่ม ThaiCERT

ตัวเลข % คือ เพดานการมองเห็นจากภายนอกแบบไม่ล็อกอิน (remote unauthenticated) ของกลุ่มนั้น — ไม่ใช่ความแม่นรายกรณี

กลุ่มประเภทระบบเพดานทำไมได้เท่านี้
1เว็บไซต์ & ระบบภายใน (CMS)88%CMS โชว์ตัวเองง่าย (meta generator, /wp-content/, readme, ปลั๊กอิน) → ได้ทั้งชนิด+เวอร์ชัน
2หลังบ้านแอป & API (Framework)60%เฟรมเวิร์กซ่อนตัวเก่ง ไม่ค่อยโชว์เวอร์ชัน จับได้เมื่อมี debug เปิดทิ้ง
3Hosting Control Panel75%มีพอร์ต/หน้าล็อกอินเฉพาะตัว + มักโชว์เวอร์ชัน

5Container & Docker45%อยู่ข้างในหลัง reverse-proxy เห็นเฉพาะเมื่อพอร์ตเผลอเปิด (2375/5000/6443)

—ค่าเฉลี่ยทั้ง 8 กลุ่ม65%เห็นจากภายนอกได้ราว 2 ใน 3 ที่เหลือต้องยืนยันบนเครื่อง
หลักการ: ยิ่งระบบ "โชว์เวอร์ชัน/ร่องรอยออกมาเอง" → % ยิ่งสูง · ยิ่งพื้นผิวเสี่ยง "ซ่อนข้างใน หรือเป็นข้อมูลองค์กร" → % ยิ่งต่ำ

11 · คำถามที่พบบ่อย (เชิงลึก)

เทียบ "ความแม่น" กับระบบสแกนเชิงพาณิชย์ (Commercial Scanner) ได้ไหม?

ตอบตรงๆ: เป็นคนละระดับและคนละวัตถุประสงค์ — เครื่องมือเราคือ "ตัวคัดกรองจากภายนอก" ส่วนระบบเชิงพาณิชย์ระดับองค์กรคือ "ตัวยืนยันเชิงลึก" จึงไม่ควรเคลมว่าแม่นเท่ากัน แต่เราก็มีจุดที่ทำได้ดีในบริบทของตัวเอง

มิติSecurity Audit Toolkit (เรา)ระบบสแกนเชิงพาณิชย์
วิธีสแกนremote ไม่ล็อกอิน (unauthenticated)credentialed / มี agent — อ่านเวอร์ชันแพตช์จริงในเครื่อง
คลังช่องโหว่ชุดคัดสรร + ค้นออนไลน์ (CIRCL)หลักหมื่น–แสน CVE ครอบคลุมทุกชั้น
ความถี่อัปเดตแก้/เพิ่มเองเป็นรอบทีมวิจัยอัปเดตต่อเนื่อง (รายวัน)
การยืนยันผลพื้นฐาน + RCE verify เฉพาะบางช่องโหว่QA + asset model + การ validate เป็นระบบ
ขอบเขตเว็บ/PHP/โครงสร้างที่หันออกเน็ตOS/DB/network/cloud/compliance
ภาษา/มาตรฐานไทย + แมป 8 กลุ่ม ThaiCERT ในตัวสากล (ปรับเป็นไทย/ThaiCERT ต้องทำเพิ่ม)
ค่าใช้จ่ายฟรี / โอเพนซอร์สมีค่าลิขสิทธิ์ (มักคิดตามจำนวนสินทรัพย์)
จุดแข็งของเรา: ออกแบบเพื่อทีม CERT ของมหาวิทยาลัยโดยเฉพาะ — ไฟล์เดียว ติดตั้งง่าย รายงานภาษาไทย แมป 8 กลุ่ม ThaiCERT มี RCE verify + chain-of-custody · เหมาะเป็น เครื่องมือคัดกรอง/triage จากภายนอกที่เร็วและเบา ใช้เสริมกับระบบเชิงพาณิชย์ ไม่ใช่มาแทนที่
แนวทางที่ดี: ใช้เครื่องมือเราคัดกรอง/ตรวจรอบนอกอย่างรวดเร็วก่อน แล้วส่งต่อให้ระบบสแกนเชิงพาณิชย์ (หรือ credentialed scanner) ยืนยันเชิงลึกสำหรับระบบที่ต้องการความแม่นสูง

Online CVE ทำงานยังไง · จะโดนแบนไหม?

เรียก API ฟรี CIRCL cve-search (cve.circl.lu) ยิง 1 ครั้งต่อ 1 (ผู้ผลิต, ผลิตภัณฑ์) ที่ตรวจพบ แล้วกรองเฉพาะ CVE ที่เวอร์ชันเข้าข่าย

สิ่งที่ช่วยไม่ให้ยิงมากเกิน: มี แคชต่อผลิตภัณฑ์ทั้ง process (สแกน 200 โฮสต์ที่เป็น NGINX เหมือนกัน ยิงจริงครั้งเดียว), จำกัด ขนานไม่เกิน 6, ใช้ User-Agent ซื่อสัตย์, และถ้า error/ถูกบล็อก จะหยุดเงียบ ไม่กระหน่ำ

โอกาสโดนแบน: ต่ำสำหรับใช้งานปกติ อย่างแย่สุดคือโดน rate-limit ชั่วคราวแล้วรอบนั้นไม่ได้ผล online (ไม่ล่ม) · จุดที่ควรระวัง: ยังไม่มี backoff/honor 429, แคชไม่เก็บลงดิสก์, และ api.macvendors.com (โหมด LAN) ลิมิตเข้มกว่า

ทำไมผลสแกนบางเครื่อง "ข้อมูลซ้ำซ้อน"?

เพราะหลาย "target (URL)" จริงๆ คือ เครื่องเดียวกัน:

  • Shared/virtual hosting: หลายชื่อโดเมนชี้ IP เดียวกัน (เช่น 1 IP โฮสต์ 28 โดเมน = สแกน 112 รายการ แต่เป็นเครื่องเดียว)
  • http + https + พอร์ต: ชื่อโฮสต์เดียวถูกยิงทั้ง http:// และ https:// (และ :8080/:8443) แยกกัน · ถ้า https redirect ไป http = เว็บเดียวกัน ผลเลยเหมือนกันเป๊ะ
  • เครื่องมือรายงานต่อ URL และยังไม่ dedup ตาม IP → เครื่องเดียวโผล่หลายแถว
แนวทางแก้ในอนาคต: ยุบรวมผลตาม IP ที่ resolve ได้ หรือกรอง http/https ที่ลงเอย base_url เดียวกัน

12 · แนวปฏิบัติที่ดี

  1. ขออนุญาต/นัดหมายเจ้าของระบบก่อนสแกนทุกครั้ง
  2. ถือผลเป็นการ "คัดกรอง" แล้วยืนยันซ้ำบนเครื่อง (โดยเฉพาะสถานะ unknown)
